## 业务前置卡（不懂技术也能用，照这一栏做）

| 项目 | 内容 |
|---|---|
| 所属部门 | 品牌与宣传 |
| 谁在用 | 品牌宣传、新媒体运营 |
| 当前状态 | 已上线 |
| 什么时候用 | 视频口播、字幕、公众号、海报文案要对外发布前；或一次来一批稿件时。 |
| 你要准备什么 | 稿件正文；尽量提供成片，核对字幕与文案是否一致。 |
| 你会得到什么 | 结论 + 四维评分 + 必改清单 + 可直接粘贴的改后句 + 审核台账。 |
| 大概省多少时间 | 单篇 1–2 小时 → 15 分钟（经验值，试点后按实际校准） |
| 谁来复核 | 结果只是初稿：投标、公文类内容必须人工核对原件后才能对外 |
| 一句话叫它 | `审一下这篇视频口播稿，能不能发、必须改哪几句，直接给我改后句。` |

> 用法：把上面这句话连同材料一起发给豆包（或对应的 AI 助手），按提示上传文件即可。不用改提示词，也不用写代码。
> 如果一句话不够清楚：把截止时间、项目名称、申报单位直接补在指令后面，结果会更准。


# 宣传视频文案审核

把"凭感觉审稿"变成"按同一套尺子审稿"。每一篇都走同样的五步，得到同样的结构，结论可追溯到具体扣分项，改后句可直接粘贴给员工，审完自动留痕。

## 第 0 步：先定三件事（不问用户，从稿件里看）

| 要判断的 | 怎么看 | 为什么影响审核 |
|---|---|---|
| **用途** | 对外发布 / 内部宣传 / 客户提案 / 招商路演 | 对外发布走最严合规；内部稿只看准确与逻辑 |
| **载体** | 视频口播、视频字幕、图文配文、公众号长文、海报单页 | 决定字数-时长匹配、字幕断句、版式适配是否列入检查 |
| **署名主体** | 企业自己发的，还是替活动/协会/政府发的 | 决定"主办/受邀/支持"类表述的尺度，差一个字就是风险 |

用途或署名主体看不出来，问一句即可，不要猜着审。

## 第 1 步：机检（有文本就必须先跑）

```bash
python scripts/check_copy.py --file <稿件.txt>
# 或
python scripts/check_copy.py --text "<稿件正文>"
```

脚本给出字数、预估口播时长（3.5/4/4.5 字每秒三档）、风险词命中及上下文、超长句、可疑数字与标点。机检只是**提示**，不替代判断：命中不等于违规，要看语境（引用政策原文、客观事实陈述、学术表述可豁免）。

## 第 2 步：四维评分

按 `references/rubric.md` 打分，四个维度加总 100 分：

- **A 合规与宣传风险（40）** — 涉政府/第三方名义、人物职务、绝对化用语、数据出处、素材授权
- **B 事实与信息准确（25）** — 时间地点活动全称、姓名职务、数字口径、专有名词写法
- **C 品牌调性与口径（15）** — 价值观一致性、语气层级、称谓统一、不自我拔高不贬同业
- **D 结构与传播转化（20）** — 前 3 秒钩子、字数时长匹配、信息层级、字幕可读性、结尾落点

打分必须落到具体扣分项编号（如 A2、B1），不许只写"整体感觉一般"。

## 第 3 步：结论分级

| 总分 | 结论 | 给用户的话 |
|---|---|---|
| ≥88 | **放行** | 可发，最多润色标点 |
| 75–87 | **小改放行** | 改完必改项即可发，不用再报我 |
| 60–74 | **退回修改** | 关键段落要重写，改完重新提审 |
| <60 或触任一红线 | **驳回重写** | 结构与口径都要重来 |

红线清单见 `references/compliance-rules.md`，任一项命中直接驳回，不看总分。

## 第 4 步：按场景出交付物

模板见 `references/output-templates.md`：

| 场景 | 交付 |
|---|---|
| 单篇、需要说清问题 | **单篇审核报告**：结论 + 总分 + 四维得分 + 必改项（P0/P1/P2）+ 改后建议文本 |
| 单篇、要快速放不放行 | **一屏速览**：结论 + 三个必改点 + 待补信息，10 行以内 |
| 多篇（≥2 篇或一批） | **批量台账**：一表一行，按优先级排序，先给挑出来的"必须今天处理"的几篇 |

一次收到多篇时默认走台账，并主动把 P0 项单独抽出来放在最前面。

## 视频类稿件必做的额外检查

除文本外，若拿到视频成片：抽帧核对字幕与文本是否一致、版式标题与画面主体是否对应、结尾是否有企业落板。流程与常见坑见 `references/video-script-checks.md`。**字幕与文案不一致是本类稿件最高频的硬伤**，不核就等于没审。

## 输出纪律

1. **不确定的事实标"待核实"，不要替他圆场。** 人名职务、活动全称、数据、主办单位，只要不能从稿件本身确认，一律列入"待补信息"，并说明向谁核（人事/主办方/活动通知）。
2. **改后句要能直接粘贴。** 给完整替换句，不给"建议优化一下表达"这类空话。
3. **区分"违规"和"不好看"。** 违规是红线，必须改；不好看是效果问题，标注为 P1/P2，由用户决定是否采纳。
4. **不虚构荣誉、数据、合作方。** 补写只能补逻辑衔接和结构，不能补事实。
5. **结论先行。** 用户第一眼要看到"能不能发"，不是先看一堆分析。

## 第 5 步：留痕（每篇必做，让证据自动累积）

审完立刻记账，不要等"有空再补"：

```bash
python scripts/log_review.py --id <编号> --title "<稿件标题>" --score <总分> \
    --verdict <结论> --p0 <必改项数> --p1 <建议项数> --hits <机检命中数> \
    [--cross-check] [--minutes <实际耗时>] \
    [--reason "<驳回理由>" --dimension <扣分项编号>]
```

- 本次核对了成片就加 `--cross-check`，**核片率是这套审核最核心的质量指标**
- 给了 `--reason` 就自动归并进 `calibration-log.md` 的驳回理由库，下次同类稿件前置检查
- `--minutes` 由审核人填实际用时，**不要估算、不要代填**；AI 审核不计入人工耗时
- 随时用 `python scripts/log_review.py --stats-only` 看累计：审了多少篇、平均分、拦下多少 P0、核片率

数据落在 `ledger/审核台账.csv`，与标准文件分开，可直接用 Excel 打开做复盘。

## 架构与扩展点

原则：**标准与代码分离、标准与数据分离、单一事实来源**。改标准尽量只改 `config/` 下的 JSON，不碰 `scripts/*.py`。

```
promo-video-copy-review/
├── SKILL.md                  # 本文件：流程与用法
├── config/                   # ← 标准的唯一事实来源
│   ├── scoring.json          # 四维权重、扣分项、结论线、P0/P1、override 规则
│   ├── video-profile.json    # 语速档/默认语速、长句阈值、超载/不足系数
│   ├── risk-terms.json       # 机检风险词、类别、说明、豁免上下文
│   └── ledger-schema.json     # 台账表头、附加列、维度归类
├── scripts/                  # 只读 config、不含硬编码标准
│   ├── check_copy.py         # 机检（--limit 可覆盖长句阈值）
│   └── log_review.py         # 记账/统计（--verdict 选项读 scoring.json）
├── references/               # 人读说明，数值以 config 为准
│   ├── rubric.md  compliance-rules.md  video-script-checks.md
│   ├── output-templates.md  calibration-log.md
├── assets/审核台账模板.csv    # 仅表头（建账用），不含示例/真实数据
├── ledger/审核台账.csv        # 真实业务数据，不随分发包分发
└── tests/                    # 可重复回归，fixtures 为真实样例快照
    ├── run_regression.py
    └── fixtures/
```

要做以下改动时，改哪个文件（**不要改 scripts**）：

| 想做的事 | 改哪里 |
|---|---|
| 改四维权重、加/扣分项、结论分数线（≥88 等）、P0/P1 定义、override 规则 | `config/scoring.json` |
| 给机检加风险词、改类别/说明、加豁免上下文（如"第一时间"） | `config/risk-terms.json` 的 `terms` / `special_terms` / `exclude_patterns` |
| 调语速档、默认语速、长句阈值、超载/不足系数 | `config/video-profile.json`（临时单次用 `--limit` 覆盖长句阈值） |
| 给台账加列、改维度归类（A/B/C→合规/事实/调性/效果） | `config/ledger-schema.json` 的 `header` / `extra_columns` / `dim_to_type` |
| 加稿件类型、改交付模板、改写法口径 | `references/` 下人读文档（涉及数值时同步回 config） |

**分发数据边界**：分发包只含源码、`config/`、`references/`、`assets/` 模板、`tests/`；**绝不**包含 `ledger/审核台账.csv`（真实审核数据），`assets/审核台账模板.csv` 只保留表头。换环境部署后首次记账自动从模板建空台账。

## 标准会越用越准

每次用户给出新口径（比如"以后涉政府活动一律写受邀出席"）、驳回理由、通过案例，追加进 `references/calibration-log.md`。下次审稿先读这个文件，按最新口径执行。这是这套标准长期有效的关键，否则会退化成通用套话。
